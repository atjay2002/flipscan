## Missing Audit Areas

The following areas were not covered by Agents 1–5 and should be audited before release:

1. **Crypto agility / key rotation.** `LockerCrypto` uses a fixed alias `flipscan_locker_v1` with no versioning or key-rotation path. If the Keystore key is ever bound to biometric (SEC-001 fix), biometric re-enrollment invalidates the key and all existing `.enc` documents become undecryptable. There is no key-rewrap or re-encryption migration path. This is directly tied to the SEC-001 fix and must be designed before that fix is implemented, otherwise fixing SEC-001 causes SEC-008-style data loss on first biometric re-enrollment.

2. **Biometric re-enrollment invalidation.** `setInvalidatedByBiometricEnrollment` is left at default false (LockerCrypto.kt lines 48-58). If the team decides to set it to true (as SEC-001 recommends considering), every biometric re-enrollment destroys the key and all locker documents. No user warning or recovery path exists. This needs a deliberate product decision plus a data-loss disclosure.

3. **Lifecycle of `lockerUntil` session vs process death.** The locker session is entirely in-memory (MainActivity.kt lines 107-108). On process death, `lockerUnlocked` resets to false, but the Keystore key (if not biometric-bound) remains usable. There is no persistent "last unlocked at" binding. This is a design limitation, not a bug, but it should be documented as a known gap if SEC-001 is not fixed.

4. **`numberVerified` write path in `LockerPinDialog`.** `DigitalPins.kt` line 250 sets `verified = value != null && PinFormat.isValid(doc.type, value)` on manual save. This means a user-typed number that passes format is marked "verified" — same semantic issue as OCR-001 but via a user action. Covered by OCR-001 but worth noting as a second write path.

5. **ML Kit model size / APK size impact.** `com.google.mlkit:text-recognition:16.0.1` is bundled (Agent 5 notes ~19.6 MB increase from v0.5.0 to v0.6.0, REL-014). No current APK/AAB size measurement exists. Should verify the release AAB stays under Play limits (200 MB) and consider whether the bundled model size is acceptable for the target device fleet.

6. **Work.clear() / filesDir/work hygiene for locker captures.** `MainActivity.discardLockerCapture()` (lines 135-138) and locker import paths call `Work.clear(ctx)`. `Work.clear` behavior and whether it reliably removes all locker-capture scratch files (including sidecars) was not deeply audited. SEC-006 touches this but a dedicated review of `Work.kt` and `Sidecar.deleteAll` would strengthen confidence.

7. **Error surface for corrupted locker index.** `LockerStore.readAll()` returns an empty list on unreadable index (line 100-103), and `readIndexOrThrow` throws if the index exists but cannot be decrypted (lines 387-391). `sweep()` returns early and deletes nothing if the index is unreadable (line 318). This is correct "don't destroy data" behavior, but the user gets no actionable error when the locker index is corrupt — the locker simply appears empty. A user-facing "locker data may be corrupted" state was not audited.

8. **Target SDK 36 behavior changes.** Raising targetSdk to 36 (REL-001) introduces Android 16 runtime behavior changes (e.g., predictive back, restricted non-resizable activities, `onBackPressed` changes). No report audited whether the app's `AnimatedContent` transitions, `BackHandler`, or portrait-only orientation behave correctly on Android 16. This is required testing before the targetSdk bump.

### Important security boundary overlooked by all five agents

None of the five reports audited the **crypto agility / key-rotation migration path** that is a hard prerequisite for the SEC-001 fix. If SEC-001 is implemented (binding the key to biometric) without a key-rewrap flow, every existing user's encrypted locker documents become permanently undecryptable on first biometric re-enrollment — converting a confidentiality improvement into a mass data-loss event. This is the most important gap: **SEC-001 and SEC-008 must be addressed together, with a re-encryption migration path, before the biometric-binding fix ships.**

### Bottom line

FlipScan v0.7.0 has a sound core architecture (AES-256-GCM per-record encryption, fresh IVs, GCM tag verification, on-device bundled OCR, strong storage isolation, no INTERNET permission, `allowBackup=false`, scoped FileProvider, bitmap recycling, off-main-thread heavy work). The genuine release blockers are all in the **Android release configuration** (REL-001/002/003/006) and the **PDF export OOM risk** (EXP-004). The highest-severity security finding (SEC-001) is real and confirmed but must be paired with a key-rewrap migration to avoid causing SEC-008-style data loss. Address the blockers and the SEC-001/SEC-002/EXP-001/EXP-004 fixes, test the release build on a physical device per TESTING.md, and the app is in good shape for v0.7.0.
